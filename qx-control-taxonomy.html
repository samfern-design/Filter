One Bar, Three Controls

A dropdown and a filter can be the same widget. What separates them is whether the control has an off state — and that single property decides counting, clearing, accenting, and what survives when the bar runs out of room.

37 controls 4 surfaces 18 of them single-select 9 filters, 9 not

The short answer

Three roles, two of which look identical.

A filter narrows a set. It has a state that means no constraint, so setting it is news — it gets an accent, a count in the All filters badge, and it is what Clear resets.

A parameter — what we have been calling a dropdown — picks a value the surface is computed from. There is no "no constraint": every table needs a frequency, a year, a universe. It always carries a value, so a set value is not news. Nothing counts it, Clear leaves it alone, and it cannot be withdrawn to an overflow menu because the table is unreadable without it.

A display control changes how the same rows are drawn — straddle or stacked, table or cards, where the heat ramp starts. Same accounting as a parameter, different reason: it is not part of the question, so it is the first thing to leave the bar and the last thing anyone needs pinned.

The test

Two questions, asked in this order, classify every control we built.

Does it have an off state — a value that means no constraint?

If yes, it is a filter. Not "does it default to off" — can it be off. Max spread defaults to nothing and can return to nothing; Frequency cannot.

In the prototype this is one property: noAll. A filter names its off state (noAll:'All', noAll:'Spot (311.51)') or accepts the default; noAll:null declares that there isn't one, and the engine stops counting and clearing it.

Does it change the numbers, or only their presentation?

Numbers means parameter: swap Frequency and every cell is recomputed. Presentation means display control: swap Straddle for Stacked and the same contracts are drawn a different way.

The consequence is withdrawal order. A parameter is pinned — you cannot read a matrix that won't say what it is measuring. A display control goes first.

Where the two blur

The single-select dropdown is the most common widget on the bar — 18 of 37 controls — and it lands on both sides of the line, nine and nine. Max spread, Min volume and Deliverables are radio lists that filter; Frequency, Month and Universe are radio lists that don't. Nothing about the widget predicts the behaviour, which is why the rule has to be a property on the control and not a component choice.

One near-miss worth knowing about. How a control acts on the data is a separate axis and not the one that matters here. Expiry, Strikes and Near re-scope rather than test rows — the same mechanism the parameters use, flagged scoped in the engine — but they each have an off state, so they are filters: counted, cleared, accented. Classify on noAll, never on how the value is applied.

The one that has no filter equivalent is a parameter that cannot render. A filter with no options is simply not applied; a parameter with no value leaves the table with nothing to compute. Whether that is a skeleton table, a disabled bar, or a blocking empty state is the biggest gap in this inventory.

Still open

Four decisions the taxonomy exposes but does not settle.

A filter sitting on its default value

Strikes defaults to ±5 and can return to All. Is ±5 "set"? Today it accents and counts, which means the bar opens with a filter already lit. The alternative is to treat an untouched default as unset — truthful to the user, but then the chip's accent no longer tracks its value.

Whether display controls belong on the bar

The chain's View rides in the chip row; the analyzer's Table/Cards sits in its own slot. Both work, and the inconsistency is currently a product decision per surface rather than a rule. Pick one before a fifth surface arrives.

Where a long list stops being a dropdown

Near carries 41 strikes behind a single-select. Search patches it, but a searchable single-select over a continuous numeric field is a different component — probably a combobox with a typed value. Somewhere between 8 and 41 options the radio list is the wrong answer; we have not said where.

Two accounting rules that leave the spec

Per-option counts and the live result count were both removed at the team's direction. Both were the spec's compensation for not being able to see into a filter before opening it, so the selection count in the popover is now the only feedback a user gets before applying. Worth watching in testing rather than assuming settled.
