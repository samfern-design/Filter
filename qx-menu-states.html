The Five Menus

Which menu opens is decided by the input mode and where you clicked — never by the filter. The same Sector control appears in four different containers, and the container changes what you can do to it.

Which menu opens

Two overrides first, then a two-by-two.

Nothing about a filter decides its menu. Read-only and gated are checked first and short-circuit everything; after that, pointer versus touch picks the family and the entry point picks the level. A filter that is unreachable on the bar — withdrawn into the overflow — is only ever reached through the trigger, so it never gets a popover of its own.

The footer inconsistency. A popover's Clear clears that one filter. The drill-down has no per-filter Clear at all — the only Clear in reach is the panel's Clear all. So on touch there is no way to empty a single filter except deselecting its options one at a time. Either the drill-down needs its own Clear in the head, or the panel footer needs to become context-sensitive.

Placement states

The popover only. The panel is edge-anchored and has none of these.

Below the chipDefault. 10px below the trigger, left edges flush — measured at every chip on all four surfaces.every flow
Flipped aboveTaken when the menu does not fit below but does fit above. In practice only controls that sit below the bar ever flip — the matrix's Highlighting is the one that does.pm-highlight

Placement measures the component's container, not the viewport — the same rule the bar uses for collapse. A filter bar embedded in a 700px widget on a 1600px screen flips and clamps against the widget, which is the only behaviour that survives being embedded.

Two rules that never fire. I measured every chip on all four surfaces at eleven widths: the clamp and the narrow path are never reached. Clamping needs a container too short for the menu either way, and narrowing needs one under 304px — neither happens down to the 360px floor. They are correct code guarding cases the current breakpoints exclude, which means either the supported minimum is wrong or the rules are speculative. Worth deciding rather than carrying.

Also: the popover's CSS width (272px) is dead — placement overwrites it with 284 on every open. A developer reading the stylesheet will get the wrong number.

What to settle

Ranked by how much rework the answer causes later.

Tab out of a popover

The clearest bug in the set. A popover is non-modal by design, so Tab should leave it — but it should close on the way out. Fixing it is a focusout handler; deciding it needs a rule for whether leaving a menu commits or discards.

Per-filter Clear on touch

The drill-down borrows the panel's footer, so Clear all is the only Clear a touch user can reach. Either the drill head gains a Clear, or the footer becomes context-sensitive at level two. The first is smaller; the second is more consistent with the popover.

Empty and loading lists

Three of the four content gaps are the same gap: the menu assumes its options exist. Once any filter's options come from a request rather than a constant, every menu needs a skeleton, an empty message, and a failure state — and the footer has to stay honest while they show.

Search visibility

Searching hides rows, including selected ones, so a user can be four selections deep and see none of them. A selected-first ordering, or a count of hidden selections, would fix it. Only bites on the long lists — Sector, Near, Index membership.

Where the anchor goes when the chip leaves

Resizing while a popover is open can withdraw its chip. Closing is defensible; handing off to the panel drilled to that filter is better and costs one branch. Rare, but it is the kind of thing that only ever gets found in a demo.
